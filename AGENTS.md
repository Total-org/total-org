# Agent instructions — Total

**Read `CLAUDE.md` for the full project guide** (architecture, hard rules, every work package's conventions, gotchas, release and deploy steps). This file is the tool-agnostic summary plus **how work is run in this repo**; if the two ever disagree on code, CLAUDE.md wins. Keep both current: a PR that changes a convention updates CLAUDE.md in the same PR, and this file when the summary or the process changes.

## What this is

Fully offline accounting app for Indian businesses — shop owners (simple mode) and their accountants / CAs (accountant mode) — on macOS first (Windows CI-tested). Electron + React + TypeScript + SQLite (better-sqlite3-multiple-ciphers): double-entry books, GST returns + e-invoice / e-way, invoice PDFs, inventory / manufacturing, banking reconciliation, Tally import, an optional AI bookkeeper (bring your own key) and a sandbox-only GST gateway. User data: one SQLite DB per company under `~/Documents/total/`. Marketing site: `site/` (Next.js 16, Vercel, root directory `site`). Public repo `Total-org/total-org`. The road to 1.0 is `docs/plan/upgrade-plan.md`; the latest audit is `docs/audit/2026-11-audit.md`.

## Working here

- Layers: `src/shared/` = pure engine (no Electron, no DB), `src/main/` = SQLite + services + Zod-validated IPC, `src/renderer/` = React UI calling `window.total.invoke` only through `src/renderer/src/lib/client.ts`.
- Money = integer paise; quantity = integer thousandths. No floats on amounts, ever.
- Reports are always computed from `voucher_lines` at query time; never store derived balances. Queries on vouchers filter binned rows (`NOT_DELETED`; `notDeletedLint.test.ts` checks it).
- Every write is audited (`writeAudit`; new channels mapped in `src/main/auditCoverage.ts`). New schema = append a migration last in `src/main/db/migrations.ts`.
- Simple-mode text goes through `t()` (en / hi / hinglish) and avoids the banned accounting words.
- Tests: `npm test` (pure engine — never import the SQLite driver), `npm run test:db` (`*.dbtest.ts`), `npm run test:renderer`, `npm run typecheck`; UI flows via `npm run build` then `node scripts/run-e2e.mjs NN` (scratch `TOTAL_DATA_DIR`, never `~/Documents/total`; unset `ELECTRON_RUN_AS_NODE`).
- Expected figures in tests are worked by hand — never generated by running the code under test, and pinned fixtures / snapshots are never regenerated to make a test pass.

## How work is run

- **One thread per work package / PR**, on its own worktree and branch from `main`. At most **2–3 feature threads at a time** (3–4 only when the owner asks); supporting threads (reviewers, helpers) don't count.
- **Review loop**: when a PR opens, its feature thread starts ONE independent review thread (Opus, high effort). The reviewer posts its findings as a PR comment and sends the feature thread the link; the feature thread fixes them, answers each finding on the PR and tells the reviewer "addressed, head `<sha>`"; the same reviewer re-reviews the new commits. Repeat until the verdict is **OK TO MERGE on the exact head** (still disagreeing after round 4 → the owner decides).
- **Merge only when**: the review says OK TO MERGE, every CI check is green on the final head (smoke-mac included), the branch is up to date with `main`, and nothing moves a figure in existing books without the owner's sign-off. Then watch `main`'s CI (e2e-mac runs only there).
- **Figures in existing books never change silently** — a change that moves a reported number comes with a before/after report and the owner's approval.
- After the merge: unwatch the PR, remove the worktree and branch, settle the review thread and then the feature thread.
- Questions only the owner can answer (figures, scope, money, anything risky) are asked plainly, recommended option first. Everything else is decided sensibly and said in the PR.
- Goal between pieces of work: zero stale PRs and one long-lived branch (`main`).

## Ship

- **Patch releases are automatic** every 12 hours (`.github/workflows/scheduled-release.yml`, ≈ 09:00 / 21:00 IST) through a strict gate: new shipped changes since the last tag, `main`'s full CI green on that commit, the upgrade test from the last release passing (figures identical unless a PR is labelled `figures-approved`), and no `release-blocker` PR. **Never tag or release by hand**; a minor bump or 1.0 is the owner's call.
- Releases publish directly (never left as drafts — the update feed reads `releases/latest`). Installed apps check the site's `/api/latest` and offer `/api/download`; silent updates arrive once builds are signed with an Apple Developer ID.
- Site: Vercel auto-deploys `site/` on every push to `main`.
